# Review Demo：三厂商交叉审查的完整现场

这是 BuddyBridge 审查链路（降级方案）的一次真实运行记录：三个不同厂商的模型，按 `REVIEW-BRIEF.md` 的约束，对同一份 `PLAN.md` 做「各自独立审 → 对抗轮互评」。**全部产物原样保留，包括每个模型犯的错。**

## 文件导览

| 文件 | 是什么 |
|---|---|
| `PLAN.md` | 被审对象：5 项最小任务计划（玩具任务，为验证机制而生） |
| `REVIEW-BRIEF.md` | 审查任务书：维度划分 / 对抗互评规则 / 多厂商路由表 / 模型自曝强制条款 |
| `REVIEW-A.md` | 第一轮·可行性+风险（kimi-k3-2，4.9KB） |
| `REVIEW-B.md` | 第一轮·验收项可验证性+完整性（deepseek-v4.1-flash，8KB） |
| `REVIEW-C.md` | **第二轮·对抗轮**（hy4-preview，22KB） |

## 怎么跑的

降级方案（multi-`-p` + `--model`，不依赖任何 preview 特性）：同一工作目录下逐次派发三条 headless 命令，每条 `--model` 指定不同厂商的模型，产物各自落盘；第三轮的任务书只给前两份报告，让它专挑漏洞。脚本见 `scripts/bb-review-run.ps1`。

## 三份报告怎么读

1. **先看每份首行**：`model: <实际使用的模型 ID> | dispatched: 降级方案单次派发` —— 模型自曝是这套机制的核心约定：路由是否生效、有没有静默退化成单模型，看这行就知道。
2. **再看 REVIEW-C 的「交叉裁决表」**（22KB 里的精华）：17 条 A/B 发现逐条裁定「成立 / 部分成立 / 降级 / 不成立」。对抗轮不是走过场——它驳回了 A 的自造要求、抓出 A-5 与 A-6 两条建议互斥、揪出 B 的判据错位（把评估器的比较策略错记在执行者的账上）和「sha256 缺口补零」的技术错误。
3. **最后看结论收敛**：第一轮 A 评「可执行」、B 评「修改后可执行」，对抗轮裁决采纳 A、驳回 B，最终统一为「可执行」。

## 这个 demo 证明了什么

- **多厂商路由由构造保证**（`--model` 是 CLI flag，不是对编排脚本的请求）——异构盲审必然生效，不需要信任任何编排层的自觉
- **对抗互评真实发生**：不同厂商的模型会犯不同的错，所以互相挑得出真问题
- **门控是配套的一环**：这三份报告之后，人工在 APPROVED.md 里写下带校验值和随机 token 的批准，执行引擎才被放行（见根目录 `templates/APPROVED.md`）
