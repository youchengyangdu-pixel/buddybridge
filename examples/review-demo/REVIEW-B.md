# REVIEW-B：验收项可验证性 + 完整性

- 审查对象：PLAN.md（v1，2026-09-25，Mini 审查与收口 Demo 5 项）
- 审查维度：验收项可验证性 + 完整性（判据口径：是否存在客观判据、goal 评估器能否仅凭对话内证据判定）
- 流程声明：第一轮独立审查，未读取 REVIEW-A.md 及任何其他轮次报告

## 一、总评

**修改后可执行。**

5 项验收项均为「文件名 + 可机械比较的文本内容」两段式结构，存在性判据客观，骨架成立；内容串在 PLAN.md 中无尾随空格/制表符歧义（已按字节核对原始文件）。但内容判据普遍缺边界约定（换行符、编码、行序、大小写），且 PROGRESS.md 行格式、STAGE-1.md 清单格式、失败态下的完成规则均未定义，导致 goal 评估器在多数场景只能靠推断而非机械判据判定。全部为文本层面可补齐项，无需重做。

## 二、发现清单

### 高（不修则评估器无法判定）

**H1. PROGRESS.md 行格式与「校验值」算法均未定义**
- 问题描述：PLAN 全文只约定了失败行格式 `编号|failed|原因`，成功行的列数、列含义、校验值所在列、校验值算法一律未出现；完成标志要求「5 行齐全零空号带校验值」，但「校验值」是 sha256/md5/长度均未写明，且与「阶段收口约定」里的 sha256 用词不一致。
- 影响哪条验收项：完成标志（PROGRESS.md 判定），并间接影响全部 5 项验收项的留痕判定。
- 建议修法：在 PLAN 内给出行格式模板，如成功行 `编号|done|<相对路径>|sha256:<64位小写hex>`、失败行 `编号|failed|<原因>`；并写明「校验值 = sha256，小写 hex，缺口补零」。

**H2. 「零空号带校验值」与「失败跳过继续」互相矛盾**
- 问题描述：失败处置允许某项 failed 并跳过继续，而 failed 行按定义没有校验值，「带校验值」对 failed 行不成立；同时「零空号」未定义——是「编号 1..5 每号必有一行」还是「所有行内容非空」，两种解释判定结果不同。
- 影响哪条验收项：完成标志；与「失败与回滚处置」条款交叉，影响 5 项验收项在失败场景下的整体判定。
- 建议修法：改写为「编号 1-5 每个编号至少一行（done 或 failed）；校验值仅对 done 行必填」。

**H3. 对话内证据不足以验证 5 个产物的内容**
- 问题描述：完成标志只要求最后一轮贴 `cat 进度文件` 与 `ls` 输出。`ls` 只能证明文件存在；PROGRESS.md 中的 sha256 由执行者自算自述，评估器无法在对话内重算比对，属自证；而完成标志同时要求「内容符合各自验收标准」——条件与证据不匹配。
- 影响哪条验收项：完成标志（全部 5 项的内容判定）。
- 建议修法：最后一轮将 5 个产物文件逐一 `cat` 贴进对话（或贴出等价的可复算内容），使内容判据可凭对话内证据复算。

**H4. 失败场景下「整体完成」无定义**
- 问题描述：失败处置规定「跳过继续」，但完成标志写的是「5 个文件全部存在」。若任一项 failed，此条恒不成立，PLAN 未说明此时 goal 应判「完成（允许带 failed）」还是「未完成」。
- 影响哪条验收项：完成标志；失败与回滚处置。
- 建议修法：补充带失败的完成判定规则，如「≥4 项 done 即本阶段完成，failed 项须在对话中列出并注明重试或放弃」。

### 中

**M5. 「一行」未定义换行符与编码（Windows 环境实际风险）**
- 问题描述：「内容一行」未约定 LF/CRLF、是否要求结尾换行、编码是否 UTF-8 无 BOM。本 Demo 在 win32 运行，评估器若按 LF 或无结尾换行做字节级比较将全部误判。
- 影响哪条验收项：2、3、4、5。
- 建议修法：全局约定「UTF-8 无 BOM；行以 LF 结尾；允许文件以单个 LF 结束；比较前统一 strip 行尾空白与 \r」。

**M6. notes.md 的行序与允许行未规定**
- 问题描述：只写「含一级标题 `# Notes` 与一行正文 `stage checkpoint test`」，未规定标题必须先于正文、两者之间是否允许空行、是否允许额外行或结尾空行。
- 影响哪条验收项：3。
- 建议修法：明确「第 1 行 `# Notes`，第 2 行 `stage checkpoint test`，无其他行（允许单个结尾换行）」。

**M7. checklist.txt 的大小写与顺序未限定**
- 问题描述：「三行：a、b、c」未写明大小写敏感、行序是否必须为 a→b→c。
- 影响哪条验收项：4。
- 建议修法：明确「精确三行，逐行等于 `a`/`b`/`c`，顺序 a、b、c，大小写敏感」。

**M8. 「Markdown 格式」不是可判定判据**
- 问题描述：Markdown 无「合法/非法」的客观定义，纯文本即退化 Markdown，此要求无法机械判定，实际只能靠 .md 扩展名。
- 影响哪条验收项：3。
- 建议修法：删除「Markdown 格式」表述，仅保留可判定的文本行判据（见 M6）与 .md 扩展名。

**M9. config.json「含两个键」的语义边界模糊**
- 问题描述：未说明键是否限定顶层、是否允许额外顶层键、值是否必须精确为字符串（如 `{"app":{"name":"bb-demo"},"version":1.0}` 是否算「含」无法判定）；「合法 JSON」未指定解析口径（任何标准解析器即可，此项相对次要）。
- 影响哪条验收项：1。
- 建议修法：把判据写死为语义式：「顶层为对象，`cfg["name"] == "bb-demo"` 且 `cfg["version"] == "1.0.0"`；额外顶层键：允许（或不允许，需择一写明）」。

**M10. STAGE-1.md 清单格式未定义**
- 问题描述：「5 项产物清单与各自 sha256」未给出格式：列表还是表格、每行列数、是否必含路径、hex 大小写。「STAGE-1.md 已生成」只能判定文件存在，内容不可判定。
- 影响哪条验收项：阶段收口约定；完成标志（STAGE-1.md 部分）。
- 建议修法：给出样例行格式并与 PROGRESS.md 统一（如 `编号|done|相对路径|sha256:<hex>`），或明确其内容须可被评估器读盘复算。

**M11. STAGE-1.md / PROGRESS.md 未编号，整体验收边界不清**
- 问题描述：PLAN 声明「预计验收项总数 5 项」且仅 5 项带编号，但完成标志把 PROGRESS.md 与 STAGE-1.md 也列为完成条件。评估器无法确定「整体通过」是「5 项产物通过即可」还是「5 项 + 两份留痕文件全齐」。
- 影响哪条验收项：验收项清单完整性；完成标志。
- 建议修法：明确「验收项 = 1-5；PROGRESS.md 与 STAGE-1.md 为收口门禁，与 5 项同时满足才算整体完成」，或将两者补编号为 6、7。

### 低

**L12. 三条约束与「顺序执行」无验证手段**
- 问题描述：「只在本目录内创建文件」「不使用任何高危命令」「顺序执行，无并行」均无对应证据要求或检查方式，goal 评估器无据可判；demo 用途下风险低。
- 影响哪条验收项：约束条款；依赖顺序条款。
- 建议修法：最低成本做法——最后一轮贴本目录 `ls -la`（时间戳可佐证实际影响范围与顺序）；或明确这三条为过程性约定、不参与机器判定。

## 三、已具备的合格点（供对抗轮检验）

- 5 项验收项均有「文件名 + 内容串」，且内容串按字节核对无尾随空格/制表符歧义，文本层判据可直接落地。
- 「预计验收项总数 5 项」与清单条目数一致，编号 1-5 无跳号。
- 完成标志覆盖「产物存在 + 收口文件 + 对话贴证」三层，方向正确，缺口仅在证据粒度与判定规则。
- 失败处置给出了明确记录格式（`编号|failed|原因`）与低成本回滚手段（删除新建文件）。
