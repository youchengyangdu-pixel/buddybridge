# REVIEW BRIEF：〈被审计划标题〉交叉审查任务书

> 本文件是引擎A（UltraCode Workflow）或降级方案（多 `-p` 分维度）的审查任务书。审查由多个并行子代理执行：各自独立审 → 对抗式互评 → 汇总上报。产出 REVIEW-REPORT.md 由**人工终裁**——未经拍板填写 APPROVED.md，被审计划不得进入执行引擎。

- 创建日期：〈日期〉
- 被审对象：〈PLAN.md 绝对路径〉
- 报告落盘路径：〈绝对路径〉/REVIEW-REPORT.md

## 心跳约定（任务开始即执行）

任务开始时先落 REVIEW-REPORT.md 骨架（状态 running + 开始时间戳），终稿完成后整体改写。监控方据此判活。

## 审查维度（每个维度一个独立代理，可增删）

1. **可行性**：技术路线是否走得通；依赖是否现实；环境假设是否成立
2. **验收项可验证性**：逐条检查验收项是否存在客观判据（**且不依赖「评估器读盘」**——goal 评估器只读对话）；挑出无法客观判定的项
3. **风险与边界**：最坏情况是什么；哪些步骤失败后无法回滚
4. **成本与规模**：工作量估计是否现实；有没有被低估的隐形步骤
5. **完整性**：缺了什么（遗漏的验收项 / 未覆盖的边界 / 缺失的回滚方案 / 幂等保护是否到位）
6. **对抗审查**：专挑前述维度审查结论的漏洞，试图推翻它们

## 对抗式互评规则

- 第一轮：各维度代理独立审查，产出发现清单（不互看）
- 第二轮：每个代理收到其他代理的发现，**专挑错误/夸大/遗漏**，给出同意/反驳意见
- 第三轮：仅上报经过互评存活下来的发现，每条标注「几个代理同意 / 几个反驳」

## 多厂商模型路由表（5 路异构盲审，默认配置）

> **强制条款**：实际生成的编排**无法**按本表路由（模型不可用/脚本未显式指定）时，必须在报告「执行元数据」节声明每个代理实际使用的模型；若实际为单模型，必须在总体评价中显式标注「本次为单模型自审，结论置信度下调」，不得伪装成多源盲审。路由必须生效时，改用降级方案（`--model` 逐次派发多 `-p`）。
>
> **思考链路**：所有审查代理一律使用其模型可用的**最高推理档位**（CLI 派发统一 `--effort max`；引擎A 路由时 per-agent 指定 effort 上限）。
>
> **滚动换新原则（实时更新）**：本表是**配置不是教条** —— 任一厂商发布更新更强的旗舰（如 kimi-k4、glm-5.4、deepseek-v5），**直接替换对应行**，无需改机制。原则只有一条：始终用**当前可用的最强旗舰**，且各路保持**异构**（不同厂商）。模型可用性以当前账号实际开通为准。

## 成本闸门

- 子代理总数上限：〈N，建议 ≤ 20〉
- 并行 fan-out 上限：〈建议 ≤ 8（官方硬上限 16）〉
- 互评轮次上限：2 轮
- 超出预算前必须先跑 1 个维度小样，按实测用量外推、人工确认再放量

## 产出格式（REVIEW-REPORT.md 结构）

1. **分歧**（放在共识之前——人工终裁最需要看的先看）：代理间意见冲突的点，并列各方论据，交人工裁决
2. **共识**：所有审查代理都认可的问题（最高优先级修改项）
3. **漏洞清单**：编号列表，每条含：问题描述 / 影响哪条验收项 / 建议修法（措辞级、可直接采纳）/ 产生该发现的模型 ID
4. **修改建议**：对 PLAN 的具体修改提案
5. **总体评价**：三选一 —— 可执行 / 修改后可执行 / 需重做（**禁止出现「批准执行/可以开工」类措辞——报告无权批准任何事，批准权只在人填写的 APPROVED.md**）
6. **执行元数据**：各代理维度 / 实际使用的模型 ID / token 用量 / 是否发生路由降级

## 门控约定
